# gokubegate 端到端测试报告

## 1. 结论

本轮在真实 kind Kubernetes 集群中完成 S1–S7 及并发压力扩展验证，10 个测试场景全部通过。
最终完整回归共处理 1,002,888 个正常权限请求。除“64 并发下每两秒快速扩缩容”这一刻意制造
Pod 强制退出竞态的场景外，其余场景零错误；快速扩缩容中有 37 次瞬时网络错误，总错误率
0.0067%，没有出现完整秒级中断。

核心结论：

- 两个 Pod 时 500 个请求精确分为 250/250；四个 Pod 时精确分为 125/125/125/125。
- 已经缩容或变为 NotReady 的 Pod 不再收到新请求。
- NotReady Pod 恢复后重新加入轮询，200 个请求精确分为 50/50/50/50。
- 稳定态各压力阶段均为零错误，连接复用率为 98.0%–99.6%。
- 无 RBAC 权限时，`NewClient` 在启动阶段失败，没有退化为绕过权限或带病运行。
- Host、用户指定 Host、path 和 query 均端到端保真。
- API Server 暂停 5.119 秒期间完成 258,653 次请求，零错误。
- 20 条并发 SSE 长流全部保持单 Pod affinity，并在四个 Pod 间 5/5/5/5 分布。
- 5,000 QPS/Pod（1c1g、10ms）目标：`pod` 模式全部 idle 档位（8/16/32/64/128）达标，
  默认 32（p99 5.74ms、零错误、精确均衡）；`clusterip` 上限约 2.7k QPS/Pod 且吞吐方差大
  （见 §5）。
- 高并发测试发现并修复了 RoundRobin 非原子计数问题；`go test -race ./...` 通过。

### S5：RBAC

默认最小权限 ServiceAccount 成功完成上述所有请求。无 RoleBinding 的 ServiceAccount 在
`NewClient` 解析 Service 端口时收到 Kubernetes `forbidden`：

```text
NewClient: gokubegate: resolve port for gokubegate-e2e/downstream:
services "downstream" is forbidden: User
"system:serviceaccount:gokubegate-e2e:gokubegate-tester-denied"
cannot get resource "services" in the namespace "gokubegate-e2e"
```

从创建失败 Job 到 harness 观测到失败共 4.053 秒，其中包含 Pod 调度、启动和 1 秒状态轮询，
不代表 `NewClient` 自身耗时。应用进程是在启动阶段直接失败，未发送下游请求。

### S6：SSE 长连接 affinity

同时建立 20 条持续约 2 秒的 SSE 流，每条流约每 50ms 返回一次 Pod identity。tester 对每条流
逐事件检查 identity，如一条流内出现两个 Pod 会立即失败。

| 指标 | 结果 |
| --- | --- |
| 流数量 | 20 |
| 成功 / 错误 | 20 / 0 |
| 单流 Pod 切换 | 0 |
| 四 Pod 分布 | 5 / 5 / 5 / 5 |

第一次扩展回归曾出现 6/5/5/4，进而发现默认 `RoundRobin` 使用普通 `uint64`，不满足其接口

单测后，SSE 定向回归和最终完整回归均稳定为 5/5/5/5。

### 64 并发持续流量下快速扩缩容

同一个 Client 持续请求 24 秒，Deployment 每 2 秒收到一次副本数变更：
`2→8→2→6→1→4`。扩容命令故意不等待前一次扩容 Ready，因此覆盖控制器反复修正期望状态的
重叠变化。

| 指标 | 结果 |
| --- | --- |
| 请求 / 成功 / 错误 | 551,753 / 551,716 / 37 |
| 总错误率 | 0.0067% |
| 吞吐 | 22,984.9 req/s |
| 连接复用率 | 98.3% |
| p50 / p95 / p99 | 1.70 / 9.09 / 13.78 ms |
| 最大延迟 | 70.72 ms |
| 最差单秒错误率 | 0.2078% |
| 完整秒级中断 | 0 |

37 次错误全部发生在快速缩到 1 Pod 的摘除窗口：31 次 `connection refused`，6 次
`connection reset by peer`。这是请求已经选择旧 Pod 后，Deployment 强制终止该 Pod 造成的
网络竞态；当前设计明确不做跨 Pod 自动重试，以避免不可安全重放请求产生重复写入。错误只出现
在一个秒级窗口，随后恢复为零。

### 发布替换：10 旧 Pod → 10 新 Pod → 旧 Pod 全部下线（pod 与 clusterip 对比）

模拟零宕机滚动发布（`TestE2ERolloutReplacement` / `TestE2ERolloutReplacementClusterIP`）：
10 个 Pod 持续运行，触发 Deployment 滚动更新（新 ReplicaSet 唯一模板标签，strategy
`maxSurge=100%` / `maxUnavailable=0`，即 10 个新 Pod 全部 Ready 后旧 10 个才下线）；
全程 128 并发持续负载 120 秒，同集群依次跑两种模式。

| 指标 | pod | clusterip |
| --- | ---: | ---: |
| 请求 / 成功 / 错误 | 10,755,864 / 10,755,463 / 401 | 477,260 / 477,156 / 104 |
| 总错误率 | 0.0037% | 0.0218% |
| 吞吐 | 89,627.0 req/s | 3,975.5 req/s |
| p50 / p95 / p99 | 0.76 / 4.58 / 8.41 ms | 2.07 / 59.79 / 768.57 ms |
| 最大延迟 | 131.56 ms | 8,474.13 ms |
| 连接复用率 | 99.1% | 99.96% |
| 轮换次数 | 0 | 522 |
| 新 Pod 首次接流量 | 第 8 秒（Ready 后当秒） | 第 9–17 秒 |
| 完整秒级中断 | 0 | 0 |

结论：

- **pod 模式满足发布场景全部预期**：错误率 0.0037%（全部是旧 Pod 下线窗口拨到已终止
  Pod 的 refused/reset）、新 Pod Ready 后当秒接入（第 8 秒）、p99 8.41ms、吞吐
  89.6k req/s、无完整秒级中断。
- **clusterip 模式不满足发布场景预期**：
  - 吞吐塌陷到 3,975 req/s（pod 的 1/22）——新 Pod 上线/旧 Pod 下线期间 kube-proxy
    endpoint 持续变化，ClusterIP 新连接不断被导到下线中 Pod，连接池处于持续重建状态；
  - 抖动严重：p99 768.57ms、最大 8.47s（pod 模式 p99 8.4ms / 最大 132ms）；
  - 新 Pod 第 9–17 秒才陆续接入（pod 模式第 8 秒当秒接入）；
  - 错误率 0.0218%（仍属低位，但为 pod 模式的 6 倍）。
- **发布/滚动场景必须使用 pod 模式**；clusterip 仅适合低并发、endpoint 稳定、无发布
  窗口的场景。
- 说明：`maxUnavailable=0` 保证旧 Pod 在新 Pod Ready 后才下线，pod 模式错误窗口只剩
  「单 Pod 终止 → EndpointSlice/快照收敛」的秒级竞态；若要进一步接近零，可在上层对
  幂等请求加可选重试（库内不默认重试）。

### clusterip 模式快速扩缩容（与 pod 模式同场对比）

为补齐 clusterip 模式在扩缩容下的实测空白，在同一个 kind 集群中依次运行
`TestE2EConcurrentRapidScaling`（pod）与 `TestE2EConcurrentRapidScalingClusterIP`
（clusterip，默认 1/1000 轮换），负载与扩缩容序列与上一场景完全一致（64 并发、24 秒、
每 2 秒 `2→8→2→6→1→4`）。

| 指标 | pod | clusterip |
| --- | ---: | ---: |
| 请求 / 成功 / 错误 | 784,365 / 784,188 / 177 | 191,625 / 191,608 / 17 |
| 总错误率 | 0.0226% | 0.0089% |
| 错误类型 | refused 104 / reset 26 / other 47 | refused 15 / other 2 |
| 吞吐 | 32,641.6 req/s | 7,240.1 req/s |
| 连接复用率 | 97.9% | 99.97% |
| 轮换次数 | 0 | 165 |
| p50 / p95 / p99 | 1.02 / 6.31 / 10.78 ms | 1.61 / 16.37 / 115.36 ms |
| 最大延迟 | 452.59 ms | 3,331.54 ms |
| 覆盖 Pod 数 | 5 | 5 |

每秒窗口的关键差异：

- **clusterip 在扩缩容时同样产生瞬时错误**：17 次错误全部发生在缩到 1 Pod 的窗口，
  dial 目标是 Service ClusterIP（10.96.1.1）——kube-proxy 把新连接导给了已终止 Pod
  （15 次 `connection refused`），另有 2 次 `cannot assign requested address`
  （客户端本地端口压力）。此前报告没有 clusterip 的缩容错误记录，只是因为该场景从未
  跑过，并非 clusterip 不出错。
- **缩到 1 Pod 后吞吐塌陷约 8 秒**：pod 模式单 Pod 阶段仍保持约 26k req/s；clusterip
  从约 20k req/s 掉到约 1k req/s，p95 从约 6ms 升到 200–1000ms。幸存 keep-alive 连接
  被 64 个 worker 排队复用（复用率 99.97%），连接池几乎不再新建连接，流量被串行化。
- **扩容收敛慢得到量化**：scale 到 4 后 EndpointSlice 约 13.6s 就绪；pod 模式新 Pod
  当秒（第 13 秒窗口）接入流量；clusterip 新 Pod 第 17 秒才首次接到请求、第 19 秒才
  铺开，且第 17–18 秒大部分流量仍集中在幸存 Pod。0.1% 轮换（165 次）在此窗口内只贡献
  了少量新连接。
- 错误率（0.0226% vs 0.0089%）不能解读为 clusterip 更可靠：clusterip 总请求量只有
  pod 的约 1/4（吞吐塌陷所致）；两者错误绝对值都很小且都集中在缩容窗口。pod 模式本轮
  额外出现 47 次 `cannot assign requested address`，集中在负载尾部，疑似快速建连/断连
  造成的客户端本地端口压力，建议在 benchmark 阶段单独观察。

### Pod 与 ClusterIP 模式对照

新增 `clusterip` 模式后，在同一四 Pod 集群中分别执行 8000 个串行请求，并对每种配置追加
64 并发、持续 5 秒的对照。该对照作为独立定向 e2e 运行，不计入前述最终全量回归请求总数。

| 配置 | Pod 分布 | 轮换次数 | 连接复用率 | 吞吐 | p99 |
| --- | --- | ---: | ---: | ---: | ---: |
| `pod` | 2000 × 4 | 0 | 99.95% | 1,266.4 req/s | 1.35ms |
| `clusterip`，轮换关闭 | 8000 / 0 / 0 / 0 | 0 | 99.99% | 1,305.5 req/s | 1.28ms |
| `clusterip`，默认 1/1000 轮换 | 5156 / 1624 / 830 / 390 | 10 | 99.86% | 1,325.7 req/s | 1.23ms |

`pod` 提供确定性请求级均衡；ClusterIP 的单 keep-alive 连接会完全粘在一个 Pod；随机关闭连接
能够逐步覆盖所有 Pod，但不会达到精确均衡。0.1% 默认值只引入很少的新建连接，单次短测试的
分布仍会有较大随机偏差。

64 并发结果：

| 配置 | 请求数 | Pod 分布 | 分布差值/总量 | 吞吐 | p95 / p99 |
| --- | ---: | --- | ---: | ---: | ---: |
| `pod` | 101,006 | 25252 / 25252 / 25251 / 25251 | <0.01% | 20,197.7 req/s | 10.61 / 16.13ms |
| `clusterip`，轮换关闭 | 74,936 | 18949 / 18786 / 18690 / 18511 | 0.58% | 14,883.9 req/s | 13.40 / 34.58ms |
| `clusterip`，默认 1/1000 | 76,284 | 19810 / 19116 / 18803 / 18555 | 1.65% | 15,241.9 req/s | 13.40 / 28.22ms |

高并发时共享 Transport 会自然建立多条 TCP 连接，因此 ClusterIP 即使关闭轮换也能覆盖全部
Pod，和 `pod` 的宏观分布差异明显缩小。默认轮换在这个 5 秒样本里没有改善瞬时均匀度；它更
适合解决低并发或长生命周期连接池的粘连，以及扩容后旧连接长期不更新的问题。

## 5. 全量模式对比与参数探索（5,000 QPS/Pod 目标，1c1g）

目标：验证「每个 1c1g 下游 Pod 承受 5,000 QPS 不出问题（10ms 内返回）」在各模式/参数下的
达成情况，并探索最合适参数（`TestE2EModeBenchmark`）。下游 Deployment 固定 4 副本并施加
1c1g 资源限制；每个配置使用独立 tester Job（干净连接池）。三个阶段：

1. 饱和（128 并发、约 12s）：记录各配置可达最大吞吐；
2. 限速验收（`-rate 20000`、10s）：精确以 5,000 QPS/Pod 施压，验收零错误、p99 ≤ 10ms、
   每 Pod 均衡；
3. 扩容收敛（2→4，128 并发）：记录新 Pod 首次接到流量的延迟。

| `pod`，idle8 | 32,842 | 8,211 | 1.06 / 16.04 / 30.64 ms | 94.9% | 0 | 0 |

### 5.3 扩容收敛（2→4，新 Pod 首次接流量延迟）

| 配置 | 新 Pod 首次接流量 | 18s 后新 Pod 流量占比 |
| --- | ---: | ---: |
| `clusterip`，无轮换 | **never（0 请求）** | 0% |
| `clusterip`，1/1000 | ~8.0 s | ~1% |
| `clusterip`，1/500 | ~6.0–8.0 s | <0.5% |
| `clusterip`，1/200 | ~4.0 s | ~2% |
| `clusterip`，1/100 | ~6.0 s | ~2% |

结论：无轮换时新 Pod 在 18 秒内完全收不到流量；开轮换后也要 4–8 秒才首次接到请求，且
18 秒后新 Pod 仅占 0.5–2% 流量。**轮换率不能可靠加速收敛**（多轮测试 3–14 秒随机波动），
收敛主要依赖高并发下连接池自然新建连接。

### 5.4 参数建议

- 目标场景（1c1g、10ms、5,000 QPS/Pod）**使用 `pod` 模式，默认 `MaxIdleConnsPerPod=32`**
  （已按此设为库默认值）：位于容量拐点（16→32 饱和 +31%，32→64 仅 +12%），目标负载下
  p99 4.57ms（六档最低）、零错误、精确均衡、复用率 99.9%，连接预算适中（32 × Pod 数 ×
  副本数）。
- 档位结论（8/16/32/64/128/512 全部达标）：idle8 最省但 p99 压线（9.95ms）、复用率低
  （95.3%），不推荐；16 可达标但容量低 24%；64 可作高余量选项（饱和 68.1k，+12%）；
  128/512 无进一步收益（约 69k 平台）。
- `clusterip` 模式不承诺 5,000 QPS/Pod（限速下约 10k req/s 上限，且吞吐方差大）；仅在
  禁止直连 Pod IP 的环境使用，轮换率保持默认 1/1000。

### 5.5 最终结论

**达标情况**：在 4 × 1c1g 下游 Pod、请求 10ms 内返回的场景下，5,000 QPS/Pod
（合计 20,000 req/s）验收**只有 `pod` 模式通过**；`clusterip` 模式全配置上限约
10.8k req/s（约 2.7k QPS/Pod），无法达标。

**各配置表现汇总**：

- `pod` 模式（idle 8/16/32/64/128/512 全部达标）：饱和容量随 idle 预算上升
  32.8k→69.9k req/s，64 后进入平台；目标负载下 p99 4.6–5.2ms（idle32/128 最低，
  idle8 压线 9.95ms）、零错误、请求级精确均衡、连接复用率 95%–99.97%。
- `clusterip` 模式（轮换率 0/100/200/500/1000）：稳态吞吐约 10k–11k req/s（约
  2.7k QPS/Pod），与轮换率基本无关；轮换只增加连接关闭次数（0→1,159）与尾部延迟
  （p99 82–229ms）；扩容时新 Pod 需 4–8 秒才接入（无轮换则 18s 内 0 流量），且 18s
  后仅占 0.5–2% 流量。

**最终推荐配置**：

1. **默认：`pod` 模式 + `MaxIdleConnsPerPod=32`**（已设为库默认值）。位于容量拐点
   （16→32 饱和 +31%，32→64 仅 +12%），目标负载 p99 4.57ms（六档最低）、零错误、
   精确均衡、复用率 99.9%，连接预算适中。
2. 高余量：`WithMaxIdleConnsPerPod(64)` 可再提升饱和容量约 12%（68.1k req/s），
   p99 仍 ≤ 10ms；128/512 无额外收益，不推荐。
3. 限制场景：不允许直连 Pod IP 时才用 `clusterip`，轮换率保持默认 1/1000；需接受
   约 2.7k QPS/Pod 的容量上限与秒级扩容收敛延迟。
4. 缩容竞态（快速缩容拨到已终止 Pod 的瞬时错误，两模式均存在、秒级窗口）：建议上层
   对幂等请求加可选重试，库内不默认重试（见 §3 快速扩缩容）。

## 6. 数据边界与后续建议

本报告中的 req/s 是单个集群内 tester 串行发请求、下游返回小 JSON 时的功能测试附带观测，
用于比较各生命周期状态是否出现明显退化，不是正式容量结论。它不包含 `NewClient` 初始化、
Job 调度或 Deployment/EndpointSlice 收敛时间，也没有覆盖并发请求、响应大包、慢请求和资源
限制下的表现。

并发梯度、持续扩缩容、SSE 和 API Server 暂停已完成。后续建议：

1. 增加持续流量中的 readiness 反复抖动和上/下游同时滚动发布。
2. 统计 FD、goroutine、heap、连接创建速率，形成独立于正确性 e2e 的正式 benchmark。
3. 对快速缩容的瞬时网络错误制定上层仅限幂等请求的可选重试策略，但库内不默认重试。
4. 对比 `clusterip` 不同轮换率在扩容收敛速度、新建连接率和资源占用上的差异（默认
   1/1000 快速扩缩容基线与 §5 全轮换率稳态/收敛对比已完成；资源占用尚未对比）。
